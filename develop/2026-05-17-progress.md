# 2026-05-16/17 工作进度

## 核心成果：Span-Based 订阅实现

### 问题背景
Per-region 订阅模型导致：
1. DDL discover 重复创建 gRPC stream（66 region → 1000+ streams），grpcio 耗尽后 split re-subscribe 静默失败
2. Region split 时 delegate 被 deregister，split 窗口内数据丢失
3. 新表（PCR 启动后 CREATE TABLE）live CDC 不稳定

### 架构演进

```
旧（Per-Region）：
  Consumer: DDL discover → per-region subscribe → N gRPC streams
  Source:   pcr_service → per-region bridge → endpoint delegate

新（Span-Based）：
  Consumer: subscribe_span(["", "")) → 1 gRPC stream
  Source:   SpanBridge → PD resolve → sub-bridge 池 → merge channel → sink
```

## Live CDC 根因修复（2026-05-17 深度学习）

### 问题
Span-based 订阅修复后，live INSERT/UPDATE/DELETE 仍然不收敛到目标端。

### 逐层追踪

| 层 | 组件 | 观察 | 结论 |
|---|------|------|------|
| 1 | raftkv `async_write` | region 42 在 live CDC 期仅 `[Put]` + `[Put, Delete]`，零个 `[Put, Put]` | Prewrite 未产生独立 DEFAULT CF 写 |
| 2 | `tikv_kv/src/lib.rs:150-156` | `From<Modify> for Request`: `cf == CF_DEFAULT` 时不调用 `set_cf()` | PutRequest.cf 为空字符串 `""` |
| 3 | `apply.rs:handle_put:1896` | `data_key_with_buffer` 对所有 CF 加 `z` 前缀 | RocksDB 所有 CF 的 key 都有 `z`（但 LOCK CF 可能有差异） |
| 4 | `delegate.rs` sink_data | `cf=lock Put` 到达但被 `put.get_cf() != "lock"` 过滤，`cf=` 的 key 匹配不到 `"default"` | DEFAULT CF 数据被双重丢弃 |
| 5 | 全量扫描 vs live CDC | full scan 直接从 RocksDB 读（key 完整）；live CDC 依赖 Raft 命令中的 key | full scan 正确，live CDC 丢失 |

### 三个修复

| # | 文件 | 修复 | 说明 |
|---|------|------|------|
| 1 | `task.rs` | rediscover/split 加 `!span_mode` 保护 | SRC Subscribe 67→1 |
| 2 | `delegate.rs` | `is_default = cf.is_empty() \|\| cf == "default"` | DEFAULT CF key 正确加 `z` 前缀 |
| 3 | `delegate.rs` | cf=lock 时调用 `Lock::parse()` 提取 `short_value` | 悲观锁小值数据提取为 DEFAULT CF |

### 关键证据

- cf= 事件: 全量 2 → live CDC 18（修复 2 生效）
- z 前缀 PCR 事件: 1 → 3+（修复 2+3 生效）
- `has_short_value=true` 日志确认锁中包含行数据（修复 3 生效）
- raftkv cmd_types 分布: `[Put]`=490, `[Put,Delete]`=668, `[Put,Put]`=273
- 目标端 CF=default flush: 208 次（全量），live CDC 数据通过 region 2 路由

### WRITE CF `z` 前缀修复（2026-05-17 最终根因）

**根因**: 官方 TiKV 中 `handle_put` 的 `data_key_with_buffer` 在 CF 判断**之前**无条件调用——所有 CF（DEFAULT、WRITE、LOCK）的 RocksDB key 都有 `z` 前缀。MVCC reader 通过 `RegionIterator::seek()` → `keys::data_key()` 加 `z` 后查找。此前「去掉 WRITE CF 的 `z` 前缀」的修复是错误的——导致 live CDC WRITE CF key 无 `z` 前缀，MVCC reader 查不到。

**修复**: `delegate.rs` 中所有 CF（包括 cf="write"）的 key 全部加 `z` 前缀，与 `handle_put` 行为一致。

**验证**:
- INSERT "Z-FIX-TEST": TGT 4/4 rows → ✅
- UPDATE id=1→"UPD": TGT 正确显示 "UPD" → ✅
- DELETE id=3: 不收敛（WriteType::Delete 单独排查）

### Batcher 稀疏写入 flush 修复（2026-05-17 最终）

**根因**: `sink_data` 末尾的 `maybe_flush_pcr_batcher()` 受 150ms 阈值限制。单次写入后若距上次 flush < 150ms，数据滞留。若该 region 后续无写入，`on_min_ts` 又未触发，数据无限期卡住（DELETE 曾被卡 1h+）。

**修复**: `sink_data` 末尾先 `maybe_flush_pcr_batcher()`（保留批量优化），再无条件 force-flush 剩余数据。

### SpanBridge Region Epoch + Event-Driven Repair（2026-05-17 架构升级）

**改动**: 
1. `resolve_regions()` 返回 `(rid, start, end, conf_ver, version)`，refresh 时对比 epoch——变化即重建 sub-bridge
2. 移除 sink repair ticker，改为 event-driven：gRPC writer 断连 → `broken_tx.send(0)` → main loop 对所有 active region schedule StartPcrStream
3. `active: HashMap<u64, RegionMeta>` 替换 `HashMap<u64, oneshot::Sender>`

**验证**: 10K DML + CREATE t2 + DROP t + CREATE t3，全部收敛零丢失。SUBS=1。

**追加修复**: `endpoint.rs` `on_start_pcr_stream` —— `has_pcr()` 为 true 时仍调用 `enable_pcr()` 更新 sink。根因：epoch 变更后旧 sub-bridge 被 cancel 但 delegate sink 未清，新 sub-bridge 的 sink 被跳过，导致新 sub-bridge 收不到 CDC 事件。

**仍开放**: sub-bridge 短命——创建后 20s-6min 即死（event channel closed），复现率 ~20%。`emit_pcr_event` 和 `enable_pcr` 处已埋诊断，下次触发自动定位。epoch refresh 能恢复，但窗口期数据丢失。

### Topology 独立 Task + spawn_blocking（2026-05-17）

## tikv-ctl raw-scan 可用（2026-05-17 验证）

**语法**: `tikv-ctl --data-dir <data_dir> raw-scan --from <from> --to <to> --limit <n> --cf <cf>`

**前提**: `--data-dir` 是全局标志（必须在 `raw-scan` 前），raft-engine 目录必须存在于 `<data_dir>/raft-engine`。若实际路径不同需 symlink。

**示例**:
```bash
tikv-ctl --data-dir /tmp/pcr-tgt-tikv raw-scan --from "zt" --to "zt01" --limit 20 --cf default
```
导致目标端 TiDB 快照停在旧的 resolved_ts，无法读取新数据。

### Span-Bridge Per-Region 竞争条件修复（2026-05-17 01:25）

**根因**: `run_event_loop` 的 `rediscover` tick（5s 间隔）在 span 模式下仍为所有 66 region 创建 per-region gRPC 订阅，触发 source 端 `enable_pcr` on delegates，与 SpanBridge sub-bridge 的 `StartPcrStream` 竞争——先到者获得 PCR event_sink，后到者被 `has_pcr()` 阻止，导致 sub-bridge event_sink 被丢弃，live CDC 事件无法流向 SpanBridge。

**修复**（`task.rs`）:
- `rediscover` tick: per-region 订阅部分加 `if !components.span_mode` 保护
- `Split` 事件处理: per-region 重订阅部分加 `if !self.span_mode` 保护
- DDL discover 已有 `span_mode` 保护（未改）
